Không phải log mới.
Là cách log có tổ chức.

Vendor sieuviet/codebase đã ghi log GELF rất tốt. Cái thiếu là một cách gọi vào đó thống nhất — theo feature, bật/tắt được, và dễ mang sang dự án khác. Đây là bản đồ của lớp tổ chức đó.

Kiến trúc

7 thư mục, mỗi cái 1 việc

Cùng 1 khuôn lặp lại 3 lần: Base… chứa logic chung, rồi Service/Queue/Cron… chỉ khai phần khác nhau.

Config/
Đọc bật/tắt feature (từ system config) — nơi duy nhất biết feature nào đang bật.
Feature/
Nơi bạn tạo file khi thêm 1 tính năng mới. AbstractFeatureObservability là lớp cha, có sẵn mọi hàm log — business code chỉ gọi vào đây, không gọi thẳng Context/Channel/Runtime.
Context/
Giữ trace_id — 1 sợi chỉ xuyên suốt dù request đi qua Service, Queue hay Cron.
Channel/
Chuẩn hoá mức log (info/warning/error…) rồi gọi (delegate) sang logger thật của vendor — không tự ghi log.
Runtime/
Ghép Context + Channel lại, kiểm tra feature có đang bật không, và có reset().
Support/
"Logger giả" — dùng khi feature đang tắt, để code gọi log vào mà không cần if/else hay null-check.
Https/
ObservabilityErrorBridge — bắt riêng lỗi PHP không ai catch (exception/warning/fatal), tách biệt với phần log nghiệp vụ ở trên.
Lý do tồn tại

Không phải để thay vendor — mà để dùng vendor tiện hơn

01

Bật/tắt theo từng tính năng

Feature nào đã ổn định, không còn phát sinh lỗi thì tắt log của riêng nó đi — không cần log thứ không bao giờ lỗi. Không cần deploy lại, chỉ đổi config.

02

Định vị lỗi đang ở đâu

Mỗi feature có event code riêng (employer_auto_approve.*), nên khi hệ thống có vấn đề, biết ngay đang lỗi ở nghiệp vụ nào, không phải mò cả rừng log chung.

03

Mang được sang dự án khác

Khuôn "1 base + 3 lớp con + feature toggle" này không gắn chặt vào PHP/Phalcon — dự án ngôn ngữ khác chỉ cần viết lại đúng khuôn đó theo cách của ngôn ngữ đó.

Vận hành

1 lượt log đi qua đâu, và thêm 1 nhánh mới thì sao

Khi business code gọi 1 dòng log

Feature::serviceLog() → Runtime kiểm tra feature có bật không? │ ├─ TẮT → trả về NullObservabilityStream (gọi gì cũng "nuốt", không lỗi, không log) │ └─ BẬT → Context lấy trace_id → Channel chuẩn hoá level → gọi logger thật (vendor) → ghi ra file/Graylog

Muốn thêm 1 luồng mới (vd 1 kiểu channel khác)?

Không đụng gì tới Service/Queue/Cron đang chạy — chỉ thêm 3 file mới cùng khuôn có sẵn:

1. XxxContext extends BaseContext — chỉ nếu cần lưu thêm dữ liệu phiên riêng 2. XxxChannel extends BaseChannel — khai mức log hợp lệ + nơi gọi logger thật 3. XxxRuntime extends BaseRuntime — 2 hàm: openContext() và current() 4. Thêm 3 hàm mới vào AbstractFeatureObservability (vd xxxLog(), xxxContext())
Cách dùng

Thêm 1 tính năng mới — từng bước

1

Tạo file trong Feature/App (hoặc Frontend)

Extends AbstractFeatureObservability, chỉ cần khai code() — đây là tiền tố cho mọi event code của feature này.

2

Xem code nghiệp vụ đang chạy ở đâu, rồi khai đúng chỗ đó

1 feature có thể dùng cả 3, tuỳ nơi gọi:

// Không cần khai gì thêm — gọi thẳng, request tự có trace_id XxxObservability::serviceLog('info', 'customer.updated', '...', [...]);
// Khai 1 lần ngay khi nhận được message, trước khi xử lý XxxObservability::queueContext(['queue_name' => $q, 'message_id' => $id], $incomingTraceId); XxxObservability::queueLog(QueueChannel::LEVEL_INFO, '...', '...', [...]);
// Khai 1 lần ngay khi job bắt đầu chạy XxxObservability::cronContext(['command' => $cmd, 'job_name' => $job]); XxxObservability::cronLog('info', '...', '...');

3 mức bật/tắt — phải ĐÚNG CẢ 3 mới thấy log

MỨC 1
env GRAYLOG_ENABLED
Công tắc tổng ngoài cùng — tắt là tắt sạch, kể cả ObservabilityErrorBridge.
MỨC 2
config.enabled_default
Công tắc tổng của riêng Observability — tắt thì mọi feature đều tắt theo.
MỨC 3
config.features.<code>
Bật/tắt riêng từng feature — không khai trong này thì mặc định TẮT.
⚠  Chỉ cần thiết trong 1 trường hợp cụ thể

reset() để làm gì — và khi nào KHÔNG cần?

Không cần với Service (HTTP) hay 1 script CLI chạy-rồi-thoát: mỗi request/mỗi lần chạy vốn đã là 1 process riêng biệt — PHP tự dọn sạch mọi static state khi request kết thúc. Gọi reset() ở đây gần như không có tác dụng gì thêm.

Bắt buộc với Queue consumer (và cron dạng vòng lặp xử lý nhiều batch trong 1 lần chạy): 1 process PHP sống xuyên nhiều message — nhìn code consumer thật (RabbitQueue::receive()) sẽ thấy đúng 1 vòng lặp while ($channel->callbacks) { $channel->wait(); } gọi callback liên tục cho từng message, KHÔNG restart process giữa các message. Vì Context/Channel là static, không reset thì trace_id và cache của message trước dính sang message sau.

$rabbitQueue->receive($params); // bên trong: while ($channel->callbacks) { $channel->wait(); } // -> 1 process, N message. Mỗi callback xử lý xong PHẢI reset(): try {   // xử lý 1 message } finally {   XxxObservability::reset(); }
Tham khảo

4 event code — 1 lỗi rơi vào đúng 1 trong 4

php.error.uncaught

Warning/notice

Không phải exception, không có throw. Request KHÔNG dừng — code chạy tiếp ngay sau dòng gây lỗi.

php.exception.caught

Exception ĐÃ có nơi bắt

Dù cố ý throw (điều khiển luồng) hay bug thật — có dispatch:beforeException/reportCaught() bắt trước. Response vẫn xử lý tiếp bình thường.

php.exception.uncaught

\Error thật, không ai bắt

KHÔNG phải throw new Exception cố ý — là \Error thật của PHP (TypeError...), lọt qua hết mọi catch(\Exception). Request DỪNG ở đây.

php.shutdown.fatal

Chết hẳn

Hết memory / quá giờ chạy — script chết ngay lúc đó, không handler nào kịp bắt. Duy nhất KHÔNG có response tử tế nào nữa.
